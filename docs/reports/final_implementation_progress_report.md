# Final Implementation Progress Report

**Project:** Ontology-Calibrated Counterfactual Explanations for Anomaly Detection in EHR Sequences
**Author:** Alireza Yegane · **Supervisor:** Professor Xuyun Zhang
**Affiliation:** Macquarie University, Faculty of Science and Engineering
**Scope of evidence:** MIMIC-IV, leakage-controlled benchmark-v2 · **Repository status:** finalized (Phase 8 complete)

---

## 1. Project Aim and Initial Direction

The project set out to detect clinically anomalous patterns in sequential electronic
health record (EHR) data and, just as importantly, to explain them. The motivating
observation was that many errors in coded hospital records are not rare events in the
statistical sense; they are *combinations* of otherwise common codes that do not make
clinical sense together — for example, a sex-specific diagnosis recorded against the wrong
sex, or a medication present without the diagnosis that would justify it.

The original design combined four ideas that each looked promising in the literature: a
sequence-based anomaly detector to learn what a normal admission looks like, an ontology
calibration layer to encode clinical constraints from SNOMED CT and RxNorm, a
generative/diffusion "surprise" score to flag unlikely sequences, and a counterfactual
explanation module to propose minimal edits that would make a flagged record coherent
again. The intended contribution was a single, interpretable pipeline in which these
components reinforced one another, with the counterfactual explanation as the novelty
anchor. This report describes how that plan met the evidence, what survived, and what did
not.

## 2. Early Implementation and Pipeline Setup

The first stage of work was infrastructural and unglamorous, but it determined everything
that followed. We built extraction code to turn raw MIMIC-IV admissions into ordered
sequences of clinical tokens — diagnoses (ICD-9/10), procedures, and medications — together
with a small set of demographic fields (`gender`, `age_group`). We wrote parsers for the
licensed terminologies (SNOMED CT RF2 and RxNorm RRF) and built the crosswalks needed to
map raw codes into a shared ontology space. In parallel we set up the project scaffold: a
test suite, configuration handling, and a discipline of writing an aggregate artifact for
every experiment so that results could be inspected and re-checked later.

At this early point the "ontology" in the system was still largely a placeholder: scoring
relied on simple ICD-prefix heuristics rather than a genuinely integrated terminology, and
the anomaly benchmark was generated by a first-pass injection procedure. Both of these
would later need to be rebuilt. The value of this stage was that it produced a working
end-to-end path from data to score to explanation, which made it possible to audit each
component honestly rather than reasoning about it in the abstract.

## 3. Audit of the Original Benchmark

Before trusting any result, we audited the benchmark the results were measured on. This
turned out to be the single most consequential decision of the project. The first benchmark
injected anomalies in a way that left a statistical fingerprint: a trivial, label-free
feature — essentially "does this record contain a particular token?" — could recover the
anomaly label at a discriminative power of roughly 0.94 on the demographic-conflict cases.
In other words, a model could appear to "detect anomalies" without doing any clinical
reasoning at all, simply by keying on an artifact of how the anomalies were made.

This is a form of circularity that quietly invalidates downstream claims. If the benchmark
is trivially separable, then a high detector score says nothing about whether the method
understands clinical incoherence, and an ablation "improvement" may only reflect the model
latching onto the artifact more tightly. Recognising this early — rather than after
reporting inflated numbers — is what allowed the rest of the project to rest on solid
ground. The conclusion was that the benchmark had to be redesigned before any component
could be evaluated meaningfully.

## 4. Building the Leakage-Controlled Benchmark-v2

The redesign produced **benchmark-v2**, which became the final benchmark for all evidence.
Its guiding principle is that each anomaly must be a violation of a *relationship* between
fields, while every individual model-visible token stays common in normal records. Three
injectors implement this. Demographic incompatibility flips the `gender` field on a record
that already contains sex-specific codes, injecting *no token* — so the conflict lives
entirely in the (code, gender) relationship. Medication-indication mismatch removes the
indication diagnosis that a present drug requires, changing only a diagnosis count.
Forbidden co-occurrence adds a curated mutually-exclusive partner (type-2 versus type-1
diabetes) that is itself a common code.

The benchmark contains 30,000 records (28,014 normal, 1,986 anomalous: 423 demographic,
1,245 medication, 318 forbidden). Splits are subject-level with zero patient overlap across
train, validation, and test, and the training split is clean-normal-only so that
unsupervised training never sees an anomaly. The result is a test set of 6,307 records
(1,376 anomalies) and a validation set of 3,123. Critically, a triviality diagnostic
confirmed that the strongest label-free trivial signal is now **0.6127**, comfortably below
the 0.80 non-circularity gate we set in advance, compared with roughly 0.94 in the first
benchmark. This made benchmark-v2 a defensible foundation: improvements measured on it
reflect genuine relational reasoning rather than an injection artifact.

## 5. Moving from Placeholder Rules to Real Ontologies

With a trustworthy benchmark in place, we replaced the placeholder ICD-prefix heuristics
with a genuinely integrated ontology. Using the UMLS Metathesaurus (release 2026AA), SNOMED
CT (US edition), and RxNorm, we parsed the terminologies and built authoritative
crosswalks: ICD-9/10 diagnoses to SNOMED CT concepts and drug names to RxNorm ingredients.
Coverage on real MIMIC-IV data reached **0.80 for diagnoses and 0.78 for medications**,
meeting the thresholds we had committed to beforehand.

This step mattered because the word "ontology" in the project title had to correspond to
something real before any ontology-based claim could be made. Getting coverage this high was
not trivial: the crosswalk is many-to-many and noisy, so a naive mapping produced large
numbers of spurious concept associations. A significant part of the effort went into
disciplined filtering — keyword-constraining concept groups and anchoring rules on the
source code family — precisely so that the ontology layer would be accurate rather than
merely present. The payoff was that the system could now consult a real clinical knowledge
structure at scoring time.

## 6. Rebuilding Scoring and Rule Coverage

The scoring layer was rebuilt around the real ontology through three auditable rule
families: demographic sex-restriction, medication required-context, and diabetes-type
mutual exclusion. Each reads only model-visible clinical content and demographics; none has
access to labels or to any record of how an anomaly was injected. The engineering emphasis
here was precision. By anchoring rules on the source code family and excluding
cross-mapped variants (such as "X in pregnancy" concepts that generic codes map into), we
reduced the false-positive rate on normal records from about 0.75 under naive rule groups
to 0.13.

The effect on the ontology signal was decisive. When the rule packs were sparse, the real
ontology scorer ranked anomalies essentially at chance (ROC-AUC ~0.50). After careful,
auditable rule authoring, its standalone ranking rose to **0.7881** on the benchmark-v2 test
set. Just as informative, no single rule family reaches this level alone — demographic-only,
medication-only, and forbidden-only each sit between roughly 0.57 and 0.63 — which shows the
three families are covering genuinely different kinds of incoherence and synergising rather
than one family carrying everything. At this point the ontology had become a strong
standalone anomaly ranker, not just an interpretability decoration.

## 7. Detector and Generative Components: What We Learned

The two components we had originally expected to carry the work — the sequence detector and
the generative surprise score — are where the project's direction changed.

We trained the unsupervised next-token detector at full scale on the clean-normal-only split
(20,570 records, vocabulary ~17,900, 25 epochs on GPU). The run converged normally, but its
test ROC-AUC was **0.4525 — below chance**. This is not a training failure; it is a
consequence of the benchmark being honest. The anomalies are relational, so they carry
almost no next-token surprise: a gender flip injects no token, an indication removal deletes
a common diagnosis, and a forbidden co-occurrence adds a common code. A language-model
detector simply has nothing to grip. When we combined the detector with the ontology score,
the combination was significantly *worse* than the ontology alone, because mixing a
near-noise signal into a strong one dilutes it.

The generative/diffusion "surprise" score (`Sgen`) was put through an explicit decision gate
rather than assumed useful. On benchmark-v2 it scored **0.4868**, near random and pointing
the wrong way (anomalies scored lower than normals), and adding it to the combined score
harmed performance in a statistically credible way. The underlying generator was also
severely mode-collapsed, using only 127 of 4,587 tokens. On this evidence, `Sgen` was
removed from the core method and its weight fixed at zero (`w_gen = 0`).

Rather than keeping these components in the final method because they were part of the
original plan, we treated their weak performance as a finding. The calibrated-score
infrastructure remains in the repository — it is exactly what let us *measure* the
non-additivity — but the recommended method does not rely on it.

## 8. Counterfactual Explanation Module

The counterfactual module needed its own honesty audit. The earlier implementation was
leaky: it read the injection answer key (which code was corrupted, and how) and effectively
reversed the injection. Such a module can "repair" anything while demonstrating nothing
generalizable, so we deleted it — including its passing-but-misleading tests — rather than
retain it as a fallback.

The rewritten generator reads only model-visible fields, the real ontology, and feedback
from the independent scorer. Given a flagged record it runs a beam search for the smallest
set of ontology-valid edits (remove, add-context, or generalize) that drives the ontology
score down, preferring fewer edits, smaller ontology distance, and lower clinical risk. A
repair counts as valid only if it resolves the violation without introducing a worse one,
stays within a small edit budget, and — by construction — never touched hidden metadata.

On the benchmark-v2 test anomalies the results are strong where the ontology can see the
problem. Of 1,376 anomalies, the ontology flags 939; among those, **89.99% are validly
repaired**, with a mean reduction in ontology score of 0.644 and a median of a single edit.
Overall success across all anomalies is **61.4%**, and the gap between the two figures is
explained entirely by detection coverage: the roughly one-third of anomalies the ontology
does not flag cannot be repaired, but those are detection gaps, not repair failures. By rule
type, mutual-exclusion and missing-context repairs succeed 100% of the time, while
demographic cases succeed about 66% — limited by a small edit budget on records with many
obstetric codes, where the clinically minimal fix (correcting the recorded sex) lies outside
this phase's token-edit vocabulary.

## 9. Final Evaluation and Main Results

All final numbers come from benchmark-v2 (MIMIC-IV), with the decision threshold selected on
the validation split and applied unchanged to the test split, and with bootstrap confidence
intervals throughout.

| Variant | ROC-AUC | 95% CI | AP | F1 |
| --- | ---: | --- | ---: | ---: |
| ontology_only_real | 0.7881 | [0.774, 0.802] | 0.542 | 0.635 |
| legacy_baseline | 0.7358 | [0.720, 0.751] | 0.543 | 0.593 |
| detector_only_full | 0.4525 | [0.436, 0.470] | 0.190 | 0.361 |
| combined_real_without_sgen | 0.7036 | [0.687, 0.720] | 0.404 | 0.460 |
| Sgen diagnostic | 0.4868 | diagnostic only | diagnostic only | diagnostic only |

Two statistical conclusions carry the result, both from paired bootstrap tests:

```text
Real ontology beats the legacy baseline:   ΔROC-AUC = +0.052,  p ≈ 0
Adding the detector hurts vs ontology-only: ΔROC-AUC = -0.085,  p ≈ 0
```

The interpretation is straightforward and consistent across phases. The real ontology scorer
is the method: it significantly outperforms the legacy ICD-prefix baseline, and the
improvement is concentrated in exactly the relational case (forbidden co-occurrence) that a
real concept hierarchy captures and a flat prefix match misses. The detector is a transparent
negative result, and the combined score is worse than the ontology alone. The final
recommended method is therefore ontology-centered, `S_main = S_ont`.

## 10. External Validation and Current Limitations

We attempted external validation on the eICU database and report the outcome honestly: it is
**blocked by a schema mismatch**. eICU encodes clinical content with APACHE/body-system
tokens rather than ICD/SNOMED/RxNorm codes, so of 500 sampled records, zero mapped into the
ontology and zero rules fired. Unblocking external validation would require an APACHE-to-ICD
or APACHE-to-SNOMED crosswalk plus re-applying the benchmark-v2 injectors on eICU, both of
which are out of scope for the current work. External validation is deferred, not claimed.

The honest limitations follow from this. All final evidence is on MIMIC-IV only, so we make
no cross-database generalization claim. The anomalies are synthetic and constructed — a
controlled, ontology-backed benchmark rather than a corpus of clinician-confirmed real-world
errors. The counterfactual repairs are validated by an ontology scorer, not by clinicians, so
"validity" means an ontology violation is resolved with a minimal coherent edit, not that a
clinician endorsed the action. The rule packs are curated rather than learned, and the
medication-indication family is deliberately noisy because its clinical semantics are
genuinely ambiguous. We do not claim clinical deployment readiness, clinician-validated
repairs, external generalization, or state-of-the-art deep anomaly detection.

## 11. Repository Finalization and Reproducibility

The final phase turned a working research repository into a finished, shareable one, without
running new science. The README was rewritten to explain the project honestly, including the
negative results. A modular paper package was assembled — abstract, introduction, methods,
experiments, results, discussion, limitations, reproducibility statement, ethics and data
statement, and future work — together with a combined manuscript and a final claims matrix
that records, claim by claim, what is supported and what is not. References were drawn from
the project's own literature survey, and bibliographic details that could not be verified were
listed as to-do rather than fabricated.

A reproducibility package documents how to set up the environment, obtain the restricted data
and terminologies under the appropriate licenses, and rerun each stage, along with a manifest
describing exactly what each committed artifact contains. Throughout, the repository commits
only aggregate-level artifacts: no raw or processed patient data, no ontology dumps, no model
checkpoints, no vocabularies, and no per-record score files. A data-safety audit confirmed the
staged set was clean, and `.gitignore` was hardened with global guards against restricted
patterns. The full test suite stands at **341 passed**, and a lightweight finalization check
script verifies that the README and manuscript remain internally consistent and free of
overclaims.

## 12. Final Outcome and Next Step

The clearest way to state the outcome is that the project changed direction based on evidence.
The original plan combined a detector, an ontology layer, a generative surprise score, and a
counterfactual explainer. Tested carefully on a benchmark we could trust, the ontology
component proved to be the reliable signal, the detector and generative score did not add
value, and the counterfactual explainer worked well precisely where the ontology could see the
problem. The final contribution is therefore an ontology-centered anomaly detection and
counterfactual explanation framework, with the detector and `Sgen` retained as transparent
negative findings rather than unsupported core claims.

One of the most important outcomes of the project was not simply improving a metric, but
clarifying which parts of the original idea were actually supported by evidence. This makes
the final result scientifically stronger, not weaker: unsupported components were removed and
reported rather than hidden, and the surviving claims are backed by confidence intervals and
significance tests on a leakage-controlled benchmark. The MIMIC-IV benchmark-v2 evidence
package is complete, the repository and reproducibility package are finalized, and the single
remaining piece of work is external validation, which requires a future APACHE-to-ICD/SNOMED
crosswalk or another ontology-compatible external dataset.
